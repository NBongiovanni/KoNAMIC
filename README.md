# KoNAMIC

**Koopman-based Neural Architecture for Model Identification and Control**

KoNAMIC is a research codebase for learning Koopman-inspired dynamical models from sensor and visual data, with a focus on quadrotor identification and control. The learned latent dynamics are used both for open-loop prediction and for closed-loop control with MPC or baseline controllers.

The repository accompanies the experiments presented in the manuscript. It is primarily intended for transparency, reproducibility, and future extension of the thesis work.

## Repository status

The main training, dataset generation, simulation, and visualization pipelines are provided through dedicated entry points located in the `entrypoints/` directory. Some auxiliary scripts are still being cleaned up after recent refactoring and may require minor adjustments before being executed out of the box.

In particular:

- user-facing workflows should be launched from the scripts in `entrypoints/`;
- configuration is handled through YAML files and command-line overrides;
- several internal modules contain a file named `cli.py`, but these files are parser/helper modules and are not meant to be executed directly;
- model training is handled by a single entry point, `entrypoints/train_model.py`, for both `sensor` and `vision` modalities;
- comparison between several experiments is handled by a single entry point, `entrypoints/run_experiment_comparison.py`, for both open-loop and closed-loop results.

## Main workflows

The codebase is organized around the following main workflows.

| Workflow | Entry point | Purpose |
|---|---|---|
| Sensor dataset generation | `entrypoints/generate_sensor_dataset.py` | Generate sensor-based trajectories and save them as `.npz` datasets. |
| Vision dataset generation | `entrypoints/generate_vision_dataset.py` | Render image datasets from previously generated sensor trajectories. |
| Model training | `entrypoints/train_model.py` | Train a Koopman-inspired model from sensor or visual data. |
| Open-loop evaluation | `entrypoints/run_open_loop_simulation.py` | Evaluate a trained model by rolling it out without feedback control. |
| Closed-loop simulation | `entrypoints/run_closed_loop_simulation.py` | Run closed-loop simulations with Koopman MPC or baseline controllers. |
| Experiment comparison | `entrypoints/run_experiment_comparison.py` | Compare open-loop or closed-loop results from several experiments using a YAML preset. |

## Installation

Clone the repository and create a Python environment:
```bash
git clone https://github.com/NBongiovanni/KoNAMIC.git
cd KoNAMIC
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip install -e .
```
> Note: depending on your system and CUDA version, you may prefer to install PyTorch separately following the official PyTorch instructions before installing the remaining dependencies.

### Dataset generation

Datasets are generated in two steps. First, sensor trajectories are simulated and stored as `.npz` files. Then, for visual experiments, these trajectories are converted into image datasets.

### Sensor datasets

Sensor datasets are generated by simulating closed-loop trajectories for a selected physical system and controller.

The sensor dataset generation entry point is:

```
python entrypoints/generate_sensor_dataset.py \
  --system-name <system_name> \
  --controller <controller_type> \
  --seed <seed>
```

Required arguments are:

| Argument        | Description                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------- |
| `--system-name` | Name of the physical system to simulate, `quadrotor_2d`, `quadrotor_3d`, or `cartpole`. |
| `--controller`  | Controller used to generate closed-loop trajectories, for example `pid` or `lqr`.              |
| `--seed`        | Random seed used by the dataset-generation pipeline.                                           |

Examples:

```
python entrypoints/generate_sensor_dataset.py \
  --system-name quadrotor_2d \
  --controller pid \
  --seed 0

python entrypoints/generate_sensor_dataset.py \
  --system-name quadrotor_3d \
  --controller pid \
  --seed 0

python entrypoints/generate_sensor_dataset.py \
  --system-name cartpole \
  --controller lqr \
  --seed 0
```

The script loads the selected system specification, builds the corresponding plant, instantiates the requested controller, and runs the scenario-generation pipeline defined in the YAML configuration files.

The generated trajectories contain state, input, and reference arrays. They are saved as `.npz` files in a timestamped directory under:

```
datasets/<system_name>/<dataset_stamp>/sensor/
```

For example:

```
datasets/cartpole/2026-06-09_16-40-02/sensor/
```

Diagnostic plots are also generated to inspect the simulated trajectories, control inputs, references, and dataset statistics.

The sensor generation pipeline currently supports multiple systems through a common interface. Quadrotor datasets are typically generated with PID controllers, while CartPole datasets can be generated with an LQR controller around the upright equilibrium.

### Vision datasets

Vision datasets of a quadrotor are generated from an existing sensor dataset:

```
python entrypoints/generate_vision_dataset.py \
  --system-name quadrotor_2d \
  --dataset-stamp <sensor_dataset_stamp> \
  --system-dim 2
```

The vision pipeline loads the previously generated sensor trajectories, renders raw images, and preprocesses them into memory-mapped arrays for training. The generated files are stored in the dataset directory associated with `--dataset-stamp`.

## Training a model

A single training entry point is used for both non-visual and visual measurements:

```bash
python entrypoints/train_model.py \
  --modality <sensor_or_vision> \
  --system-name <system_name> \
  --latent-dynamics linear \
  --dataset-stamp <dataset_stamp> \
  --id <run_id> \
  --seed 0
```

For example, to train a model from non-visual measurements:

```bash
python entrypoints/train_model.py \
  --modality sensor \
  --system-name quadrotor_2d \
  --latent-dynamics linear \
  --dataset-stamp <sensor_dataset_stamp> \
  --id <run_id> \
  --seed 0
```

To train a model from visual measurements:

```bash
python entrypoints/train_model.py \
  --modality vision \
  --system-name quadrotor_2d \
  --latent-dynamics linear \
  --dataset-stamp <vision_dataset_stamp> \
  --id <run_id> \
  --seed 0
```

The selected `--modality` determines how the training data are prepared internally. With `sensor`, the entry point loads the state/input dataset directly. With `vision`, it loads the corresponding preprocessed image dataset together with the associated state/input scalers.

Typical arguments are:

| Argument | Description |
|---|---|
| `--modality` | Input modality: usually `sensor` or `vision`. |
| `--system-name` | System name, for example `quadrotor_2d`, `quadrotor_3d`, or `cartpole`. |
| `--latent-dynamics` | Latent dynamics structure, for example `linear`, `bilinear`, or another implemented model type. |
| `--dataset-stamp` | Dataset timestamp used to build the training dataloaders. |
| `--id` | Identifier used to name the training run. |
| `--seed` | Random seed. |
| `--geom_losses` / `--no-geom_losses` | Enable or disable geometric auxiliary losses when supported. |
| `--state_in_z` / `--no-state_in_z` | Enable or disable inclusion of the state in the latent representation when supported. |

Training configurations are loaded according to the selected system and modality. The final resolved configuration is saved with the run outputs.

## Open-loop evaluation

To evaluate one trained model in open loop:

```bash
python entrypoints/run_open_loop_simulation.py \
  --modality sensor \
  --system-name quadrotor_2d \
  --stamp-run <training_run_stamp> \
  --run-status interim \
  --dataset-stamp <dataset_stamp> \
  --epoch <epoch> \
  --num-steps 100 \
  --num-rollouts 30 \
  --phase val_2 \
  --seed 3
```

Useful arguments include:

| Argument | Description |
|---|---|
| `--modality` | Selects the evaluation modality. The standalone open-loop entry point currently accepts `sensor`. |
| `--system-name` | System name used by the trained run and dataset. |
| `--stamp-run` / `--stamp_run` | Training run stamp to evaluate. |
| `--run-status` | Training run status, `interim` or `final`. |
| `--dataset-stamp` | Dataset stamp used to build the evaluation dataloaders. |
| `--epoch` | Checkpoint epoch to evaluate. |
| `--num-steps` | Number of prediction steps in each rollout. |
| `--num-rollouts` | Number of rollouts to render. |
| `--phase` | Dataset split used for evaluation, for example `val_2`. |
| `--seed` | Random seed used for rollout selection. |

The script loads the selected trained model, runs open-loop rollouts, and saves the evaluation outputs and figures under the corresponding run directory.

To compare several open-loop experiments, use the shared comparison entry point with `--eval-type open_loop`:

```bash
python entrypoints/run_experiment_comparison.py \
  --eval-type open_loop \
  --preset <preset_name> \
  --system_name quadrotor_2d \
  --modality sensor
```

Comparison presets are loaded from `configs/registries/comparisons` by default. Use `--preset-file <path>` to point to another comparison registry.

## Closed-loop simulation

To run a closed-loop simulation:

```bash
python entrypoints/run_closed_loop_simulation.py \
  --modality sensor \
  --system-name quadrotor_2d \
  --scenario-level medium \
  --stamp_run <training_run_stamp> \
  --controller koopman_mpc \
  --run-status interim \
  --seed 3
```

The closed-loop CLI accepts the following controller types:

- `koopman_mpc`, for control based on a learned Koopman model;
- `pid`, for baseline PID control on supported quadrotor setups;
- `lqr`, for baseline LQR control. LQR is now available through the closed-loop simulation entry point for supported systems, with controller configurations under `configs/components/controllers/lqr/`.

The script builds the selected controller and plant, runs the configured closed-loop simulations, and then generates the associated plots.

For a baseline closed-loop simulation, select the baseline controller directly:

```bash
python entrypoints/run_closed_loop_simulation.py \
  --modality sensor \
  --system-name quadrotor_2d \
  --scenario-level medium \
  --controller lqr \
  --run-status interim \
  --seed 3
```

To compare several closed-loop experiments, use the same comparison entry point with `--eval-type closed_loop`:

```bash
python entrypoints/run_experiment_comparison.py \
  --eval-type closed_loop \
  --preset <preset_name> \
  --system_name quadrotor_2d \
  --modality sensor
```

The comparison preset selects the experiments to overlay and the trajectory type to compare. The entry point discovers the common available `rollout_*` directories for open-loop comparisons and the common available `run_*` directories for closed-loop comparisons.

## Configuration files

Most experiments are controlled by YAML configuration files. They define, among other things:

- dataset paths and dataset versions;
- model architecture and latent dimension;
- latent dynamics type;
- loss weights;
- training hyperparameters;
- prediction horizon;
- controller and MPC parameters;
- figure-generation presets.

Command-line arguments are used to select the experiment setup and to override selected configuration options. The resolved configuration is saved next to the generated results whenever applicable.

## Outputs

Depending on the workflow, the code writes:

- generated sensor trajectories;
- rendered and preprocessed image datasets;
- trained model checkpoints;
- resolved configuration files;
- scalers used for state and input normalization;
- open-loop prediction results;
- closed-loop simulation results;
- generated figures and comparison plots.

Outputs are stored in timestamped run directories to avoid overwriting previous experiments.
